# SMD window evaluation: interpretation and limitations

Source audit: 2026-10-29. This supplement describes the checked-out executable code. Existing result files are historical measurements and cannot all be assumed to have been generated by this exact revision. No metric or training implementation was changed for this audit.

## What a window result measures

The scoring helper takes the mean of the model's score map over its valid output positions. A window is labeled anomalous if **any** test anomaly falls in the corresponding output interval. This is an overlapping-window classification problem, without point adjustment. The scored output interval can be shorter than the input context, especially for cross-attention target crops. Therefore two results both named `window` can represent different tasks. See [score averaging](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/scoring.py:101), [interval bookkeeping](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/scoring.py:103), and [window labels](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:141).

Consequences derived from those operations:

- **Longer output spans change the labels.** A short anomaly makes many overlapping windows positive, including windows containing mostly normal observations. Windows can merge nearby events into one contiguous positive run.
- **Mean scoring can dilute brief anomalies.** Under a simple additive-error model, an error affecting `d` output samples contributes approximately `d/output_length` of its local amplitude to the scalar. The label remains fully positive even when that fraction is tiny. This is a plausible task mismatch, not proof that any particular trained model failed for this reason.
- **Input length and scored length are different controls.** More context may help prediction without changing labels if the output crop is fixed. Increasing output length changes both score averaging and positive prevalence. Compare matched output intervals, or explicitly label the comparison a change of operating task.
- **Overlap creates dependent examples.** Thousands of adjacent windows are not thousands of independent confirmations. A useful confidence analysis resamples machines or contiguous blocks/events, rather than individual overlapping windows.

For model comparisons, match the machine, checkpoint-selection rule, input window, scored output span, stride, crop/latency placement, and VUS settings. Report equal-machine averages and dispersion. A pooled window average weights machines according to their lengths and stride; that is a separate estimand. Suite reports expose [settings and coverage](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/experiment_suite.py:404), and cross-attention adds [context/target lengths](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/experiment_suite.py:424).

**The training-suite summary CSV mixes protocol names.** Its `window_f1` column is window calibrated F1, but the unqualified `vus_pr` and `vus_roc` columns are explicitly read from `evaluation.timeseries`. Comparing those columns as though they describe the same window task creates artificial metric disagreement. [Summary assignment](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/experiment_suite.py:560). Use `metrics.json -> evaluation -> window -> vus_pr/vus_roc` for this report. The newer inference-evaluation flattener has qualified fields such as `window_vus_pr`, but also retains unqualified timeseries aliases; [flattener](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/evaluation_summary.py:11).

## F1, VUS-PR, and VUS-ROC ask different questions

**Calibrated window F1** is ordinary binary F1 at one threshold, the chosen quantile of clean validation window scores. **Oracle window F1** is the maximum ordinary F1 over attainable score cutoffs using test labels. It is a retrospective ceiling, not a threshold discoverable from clean data. The oracle search evaluates the full precision-recall threshold list and uses `nextafter` to reconcile scikit-learn's `>=` convention with this repo's strict `>` predictions. See [oracle search](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:74), [classification](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:87), and [scikit-learn's threshold definition](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.precision_recall_curve.html).

VUS averages range-aware curve areas over a finite family of label buffers and score cutoffs. Its range recall includes an event-existence factor, so detecting some portion of more distinct ranges can improve the measure. It rewards tolerance to score/label misalignment; it does not measure whether one deployable threshold exists. This follows the [original VUS paper, Sections 3–4](https://www.vldb.org/pvldb/vol15/p2774-paparrizos.pdf) and [official authors' implementation overview](https://github.com/thedatumorg/VUS). In the local implementation, see [buffer extension](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/metrics/vus/utils/metrics_torch.py:30), [existence-weighted recall](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/metrics/vus/utils/metrics_torch.py:95), and [integration](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/metrics/vus/utils/metrics_torch.py:114).

The PR/ROC distinction is easiest to understand before range weighting. At a given threshold, with positive prevalence `pi`, precision is `pi*TPR / (pi*TPR + (1-pi)*FPR)`. Thus a small FPR can still produce many unwanted alerts when anomalies are rare. ROC summarizes sensitivity against the fraction of normal observations falsely alerted; PR summarizes sensitivity against alert purity. A model with excellent highest-ranked alerts but worse recovery of difficult anomalies can win PR while losing overall ROC. Crossing curves permit different area rankings. Changing window length also changes prevalence. Ordinary ROC is not automatically inflated merely by class imbalance; the relevant limitation is that a global ROC area may obscure performance in the low-FPR region. [Saito and Rehmsmeier's controlled simulations](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0118432) demonstrate unchanged ROC under fixed conditional score distributions, prevalence-sensitive PR, and different early-retrieval behavior.

The local VUS formulas modify these conventional rates with weighted labels and existence rewards; the ordinary prevalence formula is explanatory intuition, **not an exact identity for every buffered VUS point**. See [local VUS rates](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/metrics/vus/utils/metrics_torch.py:95).

Additional reasons for metric disagreements in this repo:

1. VUS integrates a range of thresholds; F1 uses one optimum or one clean-data quantile. A narrow lucky F1 optimum can coexist with a mediocre area. Conversely, a broad useful ranking can be badly calibrated at the default quantile.
2. VUS extends the already window-dilated labels. Buffered near misses can receive partial credit while unbuffered F1 rejects them.
3. VUS's existence factor counts detected nonzero ranges. Good coverage of one long event is different from partial coverage of many events. Ordinary window F1 weights each window, not each original incident.
4. Different machine mixtures or unmatched output geometries change the comparison. Diagnose disagreement within the **same machine, output geometry, and checkpoint** first.

For a useful detector, retain all three requested metrics, but also report precision, recall, event detection, false-alert burden, and low-FPR behavior at the chosen clean-calibrated threshold. None of the three requested metrics alone guarantees operational usefulness.

## Verified VUS configuration mismatch

The current wrapper's docstring says the argument is the direct maximum buffer. However [the executable call](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/metrics/vus/metrics.py:10) passes **`2*slidingWindow`** to the volume routine. The routine then averages integer buffer parameters from zero through that doubled maximum, inclusive. [The spec](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/specs/vus-window-semantics.md:50) says this multiplier was removed; it was not removed from the audited call. Git commit `31427a6` dated 2026-10-21 added the docstring and spec without changing that call.

For `eval_window_size=100` and scoring stride 10, window evaluation first converts to `max(1,100//10)=10` score-index units, then VUS actually integrates buffers 0–20. The largest buffer extends approximately ten window-score positions per side, about 100 original timesteps; endpoint details and the optional final off-grid window make this mapping approximate. The executable mapping is [here](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:145), with the [volume loop here](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/metrics/vus/utils/metrics_torch.py:84).

This does **not** establish that current model ordering is wrong. Models evaluated with the same actual convention can be compared under that convention. It establishes that reported configuration and prose do not completely describe the executed metric. Historical results need code provenance or re-scoring before combining different metric conventions. Record the actual effective buffer and score-index units; do not silently relabel or overwrite old values. The repo's frozen metric stack was left unchanged.

## Why stable training is not sufficient for easy thresholding

A stable validation loss supports predictable optimization, but the tail of a score distribution can move even while its mean loss hardly changes. Conversely a simple positive rescaling of every score leaves ranking and the best achievable F1 unchanged while moving the numerical threshold. Therefore raw threshold standard deviation alone mixes harmless score-unit drift with harmful changes in discrimination. Track all of:

- clean-calibrated F1 and oracle F1 over epochs, with their absolute gap;
- VUS-PR/ROC over epochs;
- calibrated and oracle thresholds, both raw and normalized by a robust clean-score scale;
- oracle's equivalent clean quantile **and whether it is inside the observed clean range**;
- width of the score-threshold and clean-quantile intervals achieving, for example, at least 95% of oracle F1;
- late-training median/IQR and the fraction of evaluated epochs within that near-oracle band;
- whether validation-selected weights land in the stable band, rather than choosing an epoch from test results.

These are recommended diagnostics, not new measurements asserted by this supplement. A threshold plateau measured on test labels is still retrospective evidence. It should inform the next clean-data selection design, not become an undisclosed test-tuning procedure. Sparse scheduled test evaluations only establish performance at the recorded epochs, not every intervening epoch.

### Equivalent clean quantile can be misleading

The [calibration diagnostic](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:95) clips the equivalent quantile to `[0,1]` if the oracle threshold lies outside the clean-score range. For clean scores `[1,2,3]`, oracle threshold `5` yields `calibration_quantile=1`, a reproduced clean threshold of `3`, and `calibration_threshold_in_range=False`. No clean empirical quantile reproduces `5`. Several epochs all reporting `q=1` can hide substantially different unreachable oracle thresholds. Conversely an out-of-range optimum may still share a prediction plateau with reachable thresholds; only an explicit F1-versus-quantile scan can determine that.

At extreme quantiles, the effective number of independent calibration observations matters. Adjacent overlapping windows can share almost all samples. A long list of such scores is not evidence that a 99.9th-percentile threshold is statistically precise. Repeat calibration on disjoint clean blocks or bootstrap blocks, and report the induced threshold and alarm-rate spread.

## Selection and validation caveats in the current code

SMD validation consists of the chronological tail of the clean training series; the default fraction is 0.1. This is useful for temporal separation, but one tail may omit operating modes appearing elsewhere or in the test period. The scaler is fit to the **entire** train file before carving out validation, so validation is not independent of preprocessing statistics. This is not test-label leakage, but should be disclosed. [Dataset split and scaling](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/data/jepa_dataset.py:120).

Final suite scoring calibrates on that held-out clean train tail and reports its source. [Calibration data and quantile](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/experiment_suite.py:377). Clean training does not by itself guarantee that the test-normal score distribution matches the calibration distribution. A large calibrated/oracle F1 gap is compatible with distribution shift, an unsuitable fixed quantile, or poor separation near the alert region; score histograms and clean/test-normal tails distinguish these explanations.

The AE/VAE loop separately saves validation-loss-selected weights and test-metric-selected checkpoints. Files named `best_test_window_*` are deliberately test-selected retrospective upper bounds. [Checkpoint candidates](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:398). Ranking them is informative about capacity, but their performance is not an unbiased deployment estimate.

The shared `Trainer.fit` retains validation-selected `jepa_model`, but additionally saves `jepa_model_best` when a test-evaluation hook improves. Its docstring's broad monitoring-only wording is incomplete. [Actual save logic](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/trainer.py:170). Furthermore, the shared evaluation hook returns **timeseries calibrated F1**, not window F1. [Hook return](/home/manos/Documents/EKETA/HYPER_AI/gits/CARLA/utils/reconstruction_baselines.py:322). Thus an older `best_f1` checkpoint may optimize a protocol excluded by this report. Inspect its selection metadata or loading code instead of inferring its purpose from its filename. This does not invalidate default validation-selected checkpoints.
